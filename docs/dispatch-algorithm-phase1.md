# تعزيز توزيع السائقين — المرحلة الأولى

الأساس: نسخة `c1d6fd6` المرفقة في Saham.zip. لا تغيير في DB أو DTO أو routes أو أسعار التوصيل. لا migrations ولا commit أو push.

## السلوك الجديد

- سياسة واحدة قابلة للترجمة إلى SQL لاختيار السائق، وتستخدم أيضًا للتحقق قبل الإسناد.
- المدينة الصحيحة، الاعتماد، التوفر، موقع خلال LocationFreshSeconds، وعدم منع الكاش للطلبات النقدية.
- رفض موقع يتجاوز ساعتنا بأكثر من دقيقتين؛ السماح بالدقيقتين مطابق لسياسة clock skew الموجودة في استقبال المواقع.
- الإسناد الآلي للسائق الخالي فقط؛ الثاني يدوي، والسقف اليدوي الأصغر بين إعداد السعة و2.
- فحص وجود إسناد نشط فعلي عند الاختيار والقبول، إضافة إلى العداد.
- الترتيب السابق بالأقرب ثم الأطول انتظارًا؛ Id يكسر التعادل الكامل بصورة ثابتة.
- الإسناد اليدوي يعيد فحص أهلية السائق البديل قبل تحرير الإسناد السابق؛ المدينة وحداثة الموقع أصبحتا شرطين فيه أيضًا.
- القبول يعيد فحص الأهلية؛ يفحص انتهاء العرض بتوقيت الخادم بعد القراءات.
- تحويل خطأ DB إلى OrderAlreadyAssigned محصور بفهرس الإسناد النشط الواحد في خدمة قبول السائق؛ الأخطاء الأخرى تبقى ظاهرة للتشخيص.

هذا ليس حلًا للتجميع الآلي أو المسارات الفعلية. المعاملة وConcurrencyStamp وفهارس DB الموجودة تبقى مسؤولة عن حماية التغيير المتزامن. الاختبارات أدناه لا تثبت سلوك EF/PostgreSQL أو ترتيب commit في ABP.

## التحقق

أضيف مشروع xUnit مستقل `test/Saham.Dispatch.Tests`، ولا يحتاج DB أو أسرار أو تشغيل workers. يحتوي 22 حالة تنفيذ (Fact/Theory) لسياسة الإنتاج، تشمل فقدان الاعتماد بعد العرض، Offline، الحظر للكاش مع السماح للمحفظة، حدود حداثة الموقع والزمن المستقبلي، اختلاف المدينة، حد الطلبين، والإعدادات الخاطئة.

من جذر المشروع بعد توفر .NET 9 SDK والاتصال اللازم لاستعادة الحزم:

```powershell
dotnet build Saham.sln
dotnet test test/Saham.Dispatch.Tests/Saham.Dispatch.Tests.csproj
```

**الحالة في بيئة إعداد التعديل:** لا يوجد dotnet/csc/mcs، لذلك لم تنفذ build أو tests. تم فحص diff وصيغة csproj ومطابقة ملفات الحزمة. لا توصف الاختبارات بأنها ناجحة قبل تشغيلها.

**بعد الدمج (2026-10-12):** طُبّق الـPatch بلا تعارض على `e132926`. `dotnet build Saham.sln` نجح بلا تحذيرات جديدة في الملفات المعدلة، و`dotnet test` → 22/22 ناجحة. فُحصت ترجمة استعلام الاختيار كاملًا بـ`ToQueryString` (Npgsql + NetTopologySuite، دون اتصال بقاعدة): يُترجم كله إلى SQL (`ST_Distance`، `NOT EXISTS`) بلا تقييم على العميل، والترتيب: المسافة ثم `COALESCE(LastTaskCompletedAt)` ثم `Id`.

**انحراف واحد عن الـPatch:** حُذف فحص `order.CanBeDispatched` الذي أضافه الـPatch في `AssignManuallyAsync`، لأنه يمنع الإسناد اليدوي لطلب بحالة `Placed` بينما `Order.MarkAssigned` يسمح بها عمدًا. حالة الطلب ما زالت تُفحص في `MarkAssigned`، وأي استثناء يُرجع كامل الـUoW، بما فيه تحرير الإسناد السابق.

**ملاحظة:** في `AcceptOfferAsync` صار فحص الأهلية يسبق `offer.Accept`. لذلك القبول المتأخر من سائق لم يعد مؤهلًا يرجع `DriverNotAvailable` بدل `OfferExpired`، والنتيجة نفسها في الحالتين: رفض بـ409 بلا إسناد.

## اختبارات تكامل مطلوبة على قاعدة اختبار منفصلة

1. التأكد من ترجمة Predicate إلى SQL عبر Npgsql/PostGIS.
2. سائقان بنفس المسافة: الأطول انتظارًا أولًا؛ التعادل الكامل ثابت.
3. عرض ثم تعليق السائق/Offline/حظر الكاش/تقادم الموقع: القبول مرفوض دون Assignment أو زيادة العداد.
4. إسناد يدوي أول أثناء عرض آلي: القبول الآلي لا يتحول إلى طلب ثانٍ؛ الإسناد الثاني يظل يدويًا.
5. خمسون محاولة قبول متزامنة لنفس العرض → إسناد واحد وعداد صحيح (TC-14).
6. إسنادان يدويان متزامنان لسائق لديه طلب → حد أقصى طلبين (TC-15)، ورفض الخاسر.
7. رفض البديل غير المؤهل لا يحرر السائق الحالي؛ الإسناد اليدوي الثالث مرفوض.
8. قبول بالتزامن مع الإلغاء أو تغيير حالة السائق: تحقق من rollback وConcurrencyStamp على DB الفعلية.
